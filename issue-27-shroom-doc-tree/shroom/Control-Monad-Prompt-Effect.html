Description

shroom's program vocabulary expressed as effectful effects: context, scoping, failure, fallback, parallelism and typed prompting, each an ordinary effect rather than a constructor in a bespoke DSL.

Context, scoping, failure, fallback, parallelism

  • Context — held in Effectful.State.Static.Local (addContextItem / context)
  • Scoping — local-style, over that same state (withContextItem / withContext)
  • The typed request itself — the Prompt dynamic effect (promptSingle / promptSingleWith / promptTools)
  • Failure — Effectful.Error.Static with Text (failWith)
  • Fallback — catchError plus context restoration (orElse)
  • Parallelism — Effectful.Concurrent.Async, explicit rather than hiding in an Applicative instance (promptPar / promptsParallel)

Which request to reach for

In ordinary code call the class method prompt (from Control.Monad.Prompt), which honours a type's Promptable strategy. promptSingle is the flat request that method defaults to: one request, never consulting Promptable. So withContext t (prompt @a) is the strategy-aware equivalent of promptSingleWith t.

Tool use (todo 10 of the shroom arc) is promptTools plus Control.Monad.Prompt.Tool's Tool effect and toolBinding: a program names the tools it may call in its own es, and promptTools assembles the ones it is given into a [ToolDef] plus a dispatcher, which runPrompt's own tool loop (below) drives one runBackendChat call at a time.

runPrompt interprets Prompt against a Backend — todo 11's narrow adapter seam — which can tell a refusal (BackendRefusal, terminal — no re-prompt fixes a model declining outright) apart from a transport failure (BackendTransportError, exactly what a retry is for). Because a Backend makes one raw call and nothing more, the propose/dispatch/observe tool cycle runs here, one call at a time, rather than inside each backend; see toolLoop (below): a round costs one step only when at least one tool call succeeds, failed calls are free, and once the budget is spent the model gets one final tool-free call to answer with what it already has.

promptSingle :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => Eff es a Source #

Request a value of type a from the LLM in one flat request: the prompt text is the type's own description, and the schema is the type's own ToSchema. It never consults a Promptable instance, so a type's prompt strategy (a deriving via Generically, a hand-written override) is silently skipped. It is the default of the class method prompt, which is what to reach for in ordinary code: for a type with the default strategy the two coincide, and for any other prompt honours the strategy while this does not. Reach for promptSingle only when a flat request is the point (inside a strategy itself, or to compare against it).

promptSingleWith :: forall a (es :: [Effect]). (Prompt :> es, State [ContextItem] :> es, Surveyable a, ToSchema a, FromJSON a) => Text -> Eff es a Source #

Like promptSingle, with an extra piece of context scoped to this request only. Equally flat: it never consults Promptable. The strategy-aware equivalent is withContext t (prompt @a).

promptTools :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => [ToolBinding (Eff es)] -> Eff es a Source #

Like promptSingle, but the model may call any of the given tools. Build each ToolBinding with toolBinding — that is only possible when the tool's Tool effect is in es, which is the compile-time denial: a program cannot offer a tool it was not itself given.

improve :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => a -> Eff es (Maybe a) Source #

Ask the model to improve a value it (or anyone) has already produced: Nothing means the given value is a good value of its type and the model is content with it, Just v' means the model returned a corrected whole value v'.

The request scopes one UserMessage onto the current context, showing the value as JSON and asking whether it is a good value of the type and satisfies every listed property, and the reply is one verdict object, {"verdict": "fine" | "improved", "value": a}, with value always present: the corrected value for improved, the given value unchanged for fine (where it is ignored; a fine reply that omits it is still accepted). The type's description (see description) goes with it, as for promptSingle. The scoped message is not kept; the raw reply is appended to the context as an AssistantMessage, as for promptSingle.

The reply goes through the same retry path as any request: an improved value that fails to parse or violates a property is re-prompted. A fine verdict is accepted only if the value passed in satisfies every Property of a; otherwise it is retried in just the same way, the correction message naming the violated properties. So Nothing always means "the original value is valid and the model is content with it".

improve is flat by construction: it never calls the type's own prompt, so a prompt strategy may call it without recursing into itself. Only the properties Surveyable can check in code are enforced; informal ones, which only the model can judge, are tracked as #26.

promptPar :: forall (es :: [Effect]) a b. Concurrent :> es => Eff es a -> Eff es b -> Eff es (a, b) Source #

Run two programs concurrently via Effectful.Concurrent.Async, returning both results. Parallelism is an explicit call here, rather than hiding inside an Applicative's (<*>).

promptsParallel :: forall (es :: [Effect]) a. Concurrent :> es => [Eff es a] -> Eff es [a] Source #

Run a list of programs concurrently, returning all results.

runPrompt :: forall (es :: [Effect]) a. (IOE :> es, Error Text :> es, State [ContextItem] :> es) => Backend (Eff es) -> PromptConfig -> Eff (Prompt ': es) a -> Eff es a Source #

Interpret Prompt against a Backend, threading context through Effectful.State.Static.Local and surfacing failure via Effectful.Error.Static. On a parse failure, a property violation or a BackendTransportError the request is retried up to maxRetries times, each time appending the offending response (as an AssistantMessage) and a UserMessage naming what went wrong. A BackendTruncated reply is retried the same way, but appends only a UserMessage saying the reply was cut off at the length limit — the half-finished text is not replayed. A BackendRefusal is terminal and consumes no retry budget — the model declining outright is not something a re-prompt fixes. debugLog emits the same before/after-call lines with the same OK / PARSE FAIL / VALIDATION FAIL / ERROR outcomes as before.

RequestPrompt passes no tools. RequestPromptTools turns its [ToolBinding] into the [ToolDef] / dispatcher pair toolLoop drives — via localSeqUnlift, since a binding's call runs in the caller's local effect stack. RequestImprove (see improve) passes no tools either, and goes through the same retry path with a verdict schema of its own.

runPromptResultEff :: Backend (Eff '[State [ContextItem], Error Text, Concurrent, IOE]) -> PromptConfig -> Eff '[Prompt, State [ContextItem], Error Text, Concurrent, IOE] a -> IO (Either Text a) Source #

Run a Prompt program end to end against a Backend: interpret Prompt, thread context via Effectful.State.Static.Local starting from an empty history, catch failure into an Either, and provide Effectful.Concurrent.Async so promptPar / promptsParallel branches run concurrently.

The Backend is a value, not a typeclass instance — build one with e.g. shroom-baikai's Control.Monad.Prompt.Baikai.claudeBackend or fileMockBackend, applied to your config. Those builders are themselves polymorphic in m (given MonadIO m), so passing one straight to this function instantiates it at the effect stack below without any extra annotation.

Runner configuration

data PromptConfig Source #

Model-independent configuration for runPrompt / runPromptResultEff.

Constructors

PromptConfig 

Fields

  • maxRetries :: Int

    Maximum number of re-prompts when a parsed value fails property validation, on a BackendTruncated reply, or on a BackendTransportError. Default: 3.

  • maxToolSteps :: Maybe Int

    Maximum number of tool-call iterations per promptTools call before giving up. Nothing means no limit. Default: 10.

  • debugLog :: Maybe (Text -> IO ())

    Optional logger called before each LLM call and after each response. Receives a human-readable Text summary. Pass Just TIO.putStrLn for stdout, or tasty-hunit's step callback in tests. Default: Nothing.

defaultPromptConfig :: PromptConfig Source #

Default PromptConfig: up to 3 retries, up to 10 tool steps, no debug logging.
