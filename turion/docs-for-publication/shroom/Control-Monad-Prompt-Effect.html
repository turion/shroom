Description

A program is an Eff es computation with Prompt in es. Context is plain state (addContextItem, withContext), failure is an error (failWith, orElse) and parallel requests use Effectful.Concurrent.Async (promptPar). runPromptResultEff runs a program against a Backend.

In ordinary code, request a value with prompt, which follows the type's Promptable strategy. promptSingle is the flat request that method defaults to, promptTools offers the model tools to call, and improve asks it to correct a value.

promptSingle :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => Eff es a Source #

Request a value of type a in one flat request: the prompt text is the type's description and the schema its ToSchema.

Note that this skips the type's Promptable strategy, such as a deriving via Generically. It is the default of prompt, which honours the strategy and is the usual choice; call promptSingle directly inside a strategy itself.

promptSingleWith :: forall a (es :: [Effect]). (Prompt :> es, State [ContextItem] :> es, Surveyable a, ToSchema a, FromJSON a) => Text -> Eff es a Source #

Like promptSingle, with an extra piece of context scoped to this request. The strategy-aware counterpart is withContext t (prompt @a).

promptTools :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => [ToolBinding (Eff es)] -> Eff es a Source #

Like promptSingle, but the model may call any of the given tools. Build each ToolBinding with toolBinding, which needs the tool's Tool effect in es: a program cannot offer a tool it was not given. maxToolSteps limits the number of tool rounds.

improve :: forall a (es :: [Effect]). (Prompt :> es, Surveyable a, ToSchema a, FromJSON a) => a -> Eff es (Maybe a) Source #

Ask the model to improve a value it (or anyone) has already produced: Nothing means the given value is a good value of its type and the model is content with it, Just v' means the model returned a corrected whole value v'.

The request shows the value as JSON in a scoped UserMessage (not kept in the context) and asks for one verdict object, {"verdict": "fine" | "improved", "value": a}. As for promptSingle, the raw reply is appended to the context as an AssistantMessage.

The reply goes through the same retry path as any request. An improved value that fails to parse or violates a property is re-prompted; so is a fine verdict when the value passed in violates a property. So Nothing always means that the original value satisfies every Property of a. Only the properties Surveyable checks in code are enforced, not informal ones that only the model can judge.

Like promptSingle, improve is flat: it does not call the type's own prompt, so a prompt strategy may call it without recursing into itself.

Running a program

runPromptResultEff :: Backend (Eff '[State [ContextItem], Error Text, Concurrent, IOE]) -> PromptConfig -> Eff '[Prompt, State [ContextItem], Error Text, Concurrent, IOE] a -> IO (Either Text a) Source #

Run a Prompt program against a Backend, starting from an empty context and returning a failure as Left. promptPar and promptsParallel run their branches concurrently.

Build the Backend with, for example, shroom-baikai's Control.Monad.Prompt.Baikai.claudeBackend or fileMockBackend. Both build a Backend m for any MonadIO m, so the result fits here without an annotation.

runPrompt :: forall (es :: [Effect]) a. (IOE :> es, Error Text :> es, State [ContextItem] :> es) => Backend (Eff es) -> PromptConfig -> Eff (Prompt ': es) a -> Eff es a Source #

Interpret Prompt against a Backend, threading context through Effectful.State.Static.Local and surfacing failure via Effectful.Error.Static.

A request is retried up to maxRetries times. After a parse failure or a property violation, the retry appends the offending response (as an AssistantMessage) and a UserMessage naming what went wrong. After a BackendTruncated reply it appends only a UserMessage saying the reply was cut off, and a BackendTransportError is retried with the context unchanged. A BackendRefusal is terminal and consumes no retry.

The Backend makes one raw call at a time, so this function runs the tool cycle of promptTools itself: it dispatches the calls the model requests, appends their results to the context and calls the Backend again, within maxToolSteps. debugLog reports each call and its outcome.

data PromptConfig Source #

Model-independent configuration for runPrompt / runPromptResultEff.

Constructors

PromptConfig 

Fields

  • maxRetries :: Int

    Maximum number of re-prompts per request. A reply that fails to parse, a parsed value that violates a property, a BackendTruncated reply and a BackendTransportError each spend one; a BackendRefusal is terminal and spends none. Default: 3.

  • maxToolSteps :: Maybe Int

    Maximum number of tool rounds per promptTools call; Nothing means no limit. A round costs one step only when at least one of its calls succeeds. Once the steps are spent, the model gets one last call without tools to answer with what it already has. Default: 10.

  • debugLog :: Maybe (Text -> IO ())

    Optional logger called before each LLM call and after each response. Receives a human-readable Text summary. Pass Just TIO.putStrLn for stdout, or tasty-hunit's step callback in tests. Default: Nothing.

defaultPromptConfig :: PromptConfig Source #

Default PromptConfig: up to 3 retries, up to 10 tool steps, no debug logging.
